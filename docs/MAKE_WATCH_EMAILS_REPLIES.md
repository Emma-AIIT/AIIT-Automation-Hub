# Watch Emails: How outbound payload works + handling incoming replies

## 1. How the outbound reply payload works (the JSON you see)

When someone clicks **Send reply** in the app, the **app** (your backend) builds the whole payload and POSTs it to your Make.com “Send email” webhook. Make.com does **not** compute `references` or `in_reply_to`; it just receives them.

### Where each value comes from

| Field | Where it comes from |
|-------|----------------------|
| **ticket_id** | The ticket the user is replying to (from the app). |
| **reply_id** | The new row in `ticket_replies` the app just inserted (UUID). |
| **to** | The ticket’s **customer email** (`support_tickets.caller_email`). |
| **subject** | `Re: ` + the ticket’s **original subject** (`support_tickets.email_subject`), with duplicate “Re:” stripped. |
| **body** / **body_plain** | What the user typed in the reply box. |
| **cc** | Optional CC the user entered (e.g. emma@allinit.com.au). |
| **message_id** | **Generated by the app**: `<ticket-{ticket_id}-{timestamp}@reply.aiit>`. Used so future replies can be tied back to this ticket. |
| **in_reply_to** | **Computed by the app**: the Message-ID we are replying to. For the **first** reply it’s the **original email’s** Message-ID (`support_tickets.email_message_id`). For **later** replies it’s the **last outbound reply’s** `message_id` from `ticket_replies`. |
| **references** | **Computed by the app**: list of all Message-IDs in the thread so far. It starts with the ticket’s `email_message_id`, then adds every `message_id` from `ticket_replies` for that ticket (newest first), and joins them with a space. So it’s: `[ticket.email_message_id, ...reply message_ids].join(" ")`. |

So **references** and **in_reply_to** are both derived in your app from:

1. The ticket’s `email_message_id` (the original incoming email’s Message-ID).
2. The `message_id` of every reply already stored in `ticket_replies` for that ticket.

Make.com “Send an Email” only needs to map `1.to`, `1.subject`, `1.body`, `1.cc` from the webhook. If the module supports custom/internet headers, you can also send `1.in_reply_to` and `1.references` (and optionally `1.message_id`) so the sent email keeps the thread in Outlook.

## 2. When an email comes in: how to treat replies vs new tickets

Right now **“AH - Watch emails to create tickets”** treats **every** new email as a potential **new** ticket (Webhook → List messages → Router → Feeder → OpenAI → Supabase `support_tickets`).

To support **replies** you need to:

1. For each **incoming** email, get its **In-Reply-To** (and optionally **References**) header.
2. Check if that value matches any **existing** thread:
   - `support_tickets.email_message_id`, or  
   - `ticket_replies.message_id`
3. **If it matches** → treat the email as a **reply** to an existing ticket: add a row to `ticket_replies` (inbound) and **do not** create a new ticket.
4. **If it does not match** → treat it as a **new** ticket and keep your current flow (OpenAI → `support_tickets`).

So the “watch emails” scenario needs a **branch before** the OpenAI + create-ticket path: **“Is this a reply?”** → if yes, add to thread; if no, create ticket.

## 3. What you need from the incoming email in Make.com

- **In-Reply-To** (and ideally **References**) so you can look up the thread.  
  In Microsoft Graph these often appear as:
  - **Message ID**: `id` or `internetMessageId` (the Message-ID of *this* email).
  - **In-Reply-To / References**: sometimes on the message object, or inside **internetMessageHeaders** (array of `{ name, value }`).

If **List messages** (module 6) doesn’t expose **In-Reply-To** and **References**, add a **Microsoft 365 Email – Get a message** step with message id = `6.id` and use the **internetMessageHeaders** (or equivalent) from that step to find the header named `In-Reply-To` (and `References`).

## 4. Suggested flow: “AH - Watch emails” with reply handling

High level:

1. **Webhook** (trigger).
2. **Microsoft 365 Email – List messages** (unread) → you get one or more messages (e.g. module **6**).
3. **Router** (e.g. module **12**):
   - **Route A – “Has In-Reply-To”**  
     - Condition: incoming email has an **In-Reply-To** (or **References**) value (from 6 or from a **Get message** step).
   - **Route B – “No In-Reply-To / new email”**  
     - Condition: no In-Reply-To (or no match in DB).  
     - This branch keeps your **current** flow: Feeder → OpenAI → filter `isSupportEmail` → Supabase `support_tickets` (and mark read, attachments, etc.).

4. **Route A – “Reply” branch**  
   - **4a. Resolve ticket_id**  
     - Search your DB for a row where:
       - **support_tickets.email_message_id** = In-Reply-To (or any Message-ID in References), **or**
       - **ticket_replies.message_id** = In-Reply-To (or any Message-ID in References).  
     - Use **Supabase – Search records** (or Run custom query):  
       - Table `ticket_replies`, filter `message_id` = `{{InReplyToValue}}` → take `ticket_id` from the first result.  
       - If no result, search table `support_tickets`, filter `email_message_id` = `{{InReplyToValue}}` → take `id` as `ticket_id`.
   - **4b. Add the reply**  
     - **HTTP – Make a request** to your app:  
       - URL: `POST https://<your-app-domain>/api/add-ticket-reply`  
       - Body (JSON):  
         - `ticket_id`: from 4a  
         - `body`: incoming email body (e.g. `6.body.content`)  
         - `body_plain`: plain text if available  
         - `from_email`: sender (e.g. from 6)  
         - `subject`: `6.subject`  
         - `message_id`: this email’s Message-ID (e.g. `6.internetMessageId` or from headers)  
         - `in_reply_to` / `references_header`: from headers if you have them  
     - Or use **Supabase – Insert record** into `ticket_replies` with `direction: 'inbound'` and the same fields.
   - **4c. Mark email as read** (and handle attachments if you want) the same way you do in the “new ticket” branch (e.g. **Update a draft message** with `isRead: true` or your current mark-read step).

5. **Route B** stays as today: Feeder → OpenAI → filter → Supabase `support_tickets` → mark read / attachments.

## 5. Matching replies when Message-ID is your custom format

Your outbound replies use:

- **message_id** = `<ticket-{ticket_id}-{timestamp}@reply.aiit>`

When the **customer** replies, their email client will set **In-Reply-To** to that value. So in Make.com you:

- Take the incoming email’s **In-Reply-To** (or the first ID in **References**).
- Search **ticket_replies** where **message_id** = that In-Reply-To string → you get **ticket_id**.
- If not found, search **support_tickets** where **email_message_id** = that string → you get **id** as **ticket_id**.

So you only need to **compare** the incoming In-Reply-To (or References) to your stored `email_message_id` and `message_id`; no need to parse the `<ticket-...@reply.aiit>` format unless you want to derive `ticket_id` from it as a fallback.

## 6. Short summary

| Question | Answer |
|----------|--------|
| How does the outbound JSON work? | The **app** builds all fields (including **references** and **in_reply_to**) from the ticket and existing `ticket_replies`, then POSTs to your Make.com webhook. Make.com just maps them into “Send an Email”. |
| Where do **references** and **in_reply_to** come from? | From the app: ticket’s `email_message_id` and every `message_id` in `ticket_replies` for that ticket. |
| How do I handle incoming replies in “Watch emails”? | After List messages, add a branch: if the email has **In-Reply-To** (or References) that matches **support_tickets.email_message_id** or **ticket_replies.message_id**, then **add to thread** (POST `/api/add-ticket-reply` or insert into `ticket_replies`); otherwise run your **existing** flow and create a new **support_tickets** row. |
